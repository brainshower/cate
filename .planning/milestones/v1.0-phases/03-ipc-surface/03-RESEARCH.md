## Existing Patterns

IPC channel names are centralized in `src/shared/ipc-channels.ts` as `UPPER_SNAKE_CASE` constants whose string values use namespaced channels such as `fs:readFile`, `workspace:update`, and `agent:create`. Add `FLASHQUERY_SET_CONNECTION`, `FLASHQUERY_LIST_VAULT`, `FLASHQUERY_GET_DOCUMENT`, `FLASHQUERY_WRITE_DOCUMENT`, and `FLASHQUERY_STATUS`. [VERIFIED: `src/shared/ipc-channels.ts`; product Requirements §6.2]

Preload exposes `window.electronAPI` through `contextBridge.exposeInMainWorld`. Invoke-style methods call `ipcRenderer.invoke(CHANNEL, ...)`; event subscriptions wrap `ipcRenderer.on(CHANNEL, listener)` and return an unsubscribe that calls `ipcRenderer.removeListener`. Add methods such as `flashquerySetConnection`, `flashqueryListVault`, `flashqueryGetDocument`, `flashqueryWriteDocument`, and `onFlashQueryStatus`. [VERIFIED: `src/preload/index.ts`, `src/shared/electron-api.d.ts`]

Main IPC modules usually export `registerHandlers(): void` and are imported into `src/main/index.ts`. Critical handlers are registered in `registerCriticalHandlers()` before deferred agent/git handlers. FlashQuery IPC is workspace/config/editor-critical for later phases, so register `registerFlashQueryHandlers(...)` in `registerCriticalHandlers()` near `registerWorkspaceHandlers()`. [VERIFIED: `src/main/index.ts`, `src/main/ipc/filesystem.ts`]

Cross-window broadcasts should use `broadcastToAll(channel, ...args)` from `src/main/windowRegistry.ts`, not direct `BrowserWindow.getAllWindows()` loops inside the FlashQuery IPC module. After the Phase 2 gap fixes, `FlashQueryClientManager.subscribe(workspaceId, 'status', handler)` emits `FlashQueryStatusPayload` directly with `workspaceId` inline; the Phase 3 bridge should broadcast that renderer-safe payload as `FLASHQUERY_STATUS` without expecting an `{ workspaceId, type, payload }` wrapper unless implementation intentionally migrates and tests the manager contract. [VERIFIED: `src/main/windowRegistry.ts`, `src/main/flashquery/clientManager.ts`; product Requirements §6.2.5]

Workspace metadata mutation already exists through `updateWorkspace(id, changes)`, which sanitizes `flashqueryConnection`, stores/clears tokens via `setWorkspaceToken`, and returns `WorkspaceMutationResult`. Phase 3 can either reuse `updateWorkspace` for persistence or extract a narrower helper, but the plan must avoid duplicating token writes in two places. After successful set/clear, call `manager.dispose(workspaceId)` so stale retry timers/client state cannot survive a config change. [VERIFIED: `src/main/workspaceManager.ts`, `src/main/flashquery/credentials.ts`, `src/main/flashquery/clientManager.ts`]

`WorkspaceInfo.flashqueryConnection` is renderer-safe because `sanitizeFlashQueryConnection` strips bearer tokens before returning workspace data. The only renderer-to-main token path allowed in v1 is the settings dialog later calling `flashquery:setConnection`; main must never broadcast the raw token back. [VERIFIED: `src/shared/types.ts`, `src/main/workspaceManager.ts`; product Requirements INV-02]

## Implementation Boundaries

Do not implement Phase 4/5/6 behavior in Phase 3. No vault panel, status chip UI, connection dialog, workspace context-menu item, editor URI routing, editor badge, conflict detection, vault document creation, frontmatter editing, or Pi/agent integration. [VERIFIED: `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`]

`flashquery:setConnection(workspaceId, connection | null)` owns validation and mutation orchestration. Non-null connections must validate `transport === 'http'` and a parseable `http:` or `https:` URL, then persist through the workspace manager so sanitized metadata and bearer-token storage stay centralized. The handler must dispose stale manager state and start/probe through the manager so `connecting` and subsequent status events broadcast. `null` clears metadata/token through the same workspace-manager path and disposes manager state; product docs allow either a no-connection status broadcast or relying on workspace metadata absence, but a deterministic disconnected/no-connection broadcast is easier to test. [VERIFIED: product Requirements §6.2.1; `src/main/workspaceManager.ts`; `src/main/flashquery/clientManager.ts`]

The manager likely needs public methods beyond Phase 2: `listVault(workspaceId, vaultPath?)`, `getDocument(workspaceId, vaultPath)`, and `writeDocument(workspaceId, vaultPath, content)`, plus a private/lazy `getConnectedClient` that loads workspace connection metadata and token in main. Keep the public methods domain-shaped rather than exposing generic `callTool` to the IPC module; this prevents UI/editor code from gaining a general FlashQuery tool executor. [VERIFIED: product Requirements §6.2; Context7 `/modelcontextprotocol/typescript-sdk` client docs]

Use the official MCP TypeScript SDK if adding an HTTP MCP client dependency: `Client` plus `StreamableHTTPClientTransport(new URL(...))`, then `client.callTool({ name, arguments })`. Bearer auth can be provided through a `StreamableHTTPClientTransport` `authProvider` or `requestInit.headers` with a Web `Headers` object. `@modelcontextprotocol/sdk` latest is `1.29.0`, repository `modelcontextprotocol/typescript-sdk`, MIT, slopcheck `[OK]`; it is not currently in Cate `package.json`, so the planner must include an explicit dependency-install task if Phase 3 implements real MCP calls rather than a local fetch transport. [VERIFIED: Context7 `/modelcontextprotocol/typescript-sdk`; VERIFIED: npm registry; VERIFIED: slopcheck]

FlashQuery HTTP transport serves public `GET /mcp/info` before auth, but all other `/mcp` routes can require bearer auth. Phase 3 tool calls should include auth only for MCP tool calls, not the info probe path already implemented in Phase 2. [VERIFIED: FlashQuery `src/mcp/server.ts`; `docs/SECURITY-TOKENS.md`; Phase 2 verification]

`flashquery:listVault` should return an empty array for unconfigured or disconnected workspaces and should not throw for that state. It should call `list_vault` only when live/connected or when lazy connection succeeds, normalize FlashQuery entries into `{ name, type: 'folder' | 'document', vaultPath, title? }`, and handle partial/per-entry failures by omitting or marking failed entries rather than rejecting the whole list. [VERIFIED: product Requirements §6.2.2; FlashQuery `src/mcp/tools/files.ts`]

`flashquery:getDocument` should reject on missing/bad documents with descriptive errors, return `{ body, version_token, modified }`, and must not retain `version_token` in global state. The tool call shape must use `identifiers: vaultPath` and `include: ['body']` exactly; no `frontmatter` or `headings`. [VERIFIED: product Requirements §6.2.3; FlashQuery `src/mcp/tools/documents/get.ts`; product Test Plan §4.3.3]

`flashquery:writeDocument` should return structured results rather than throwing for transport/tool failure: `{ success: true, modified }` or `{ success: false, error }`. The tool call must never include `frontmatter`, `title`, `tags`, `expected_version`, or `if_match`, and must never send `mode: 'create'`. [VERIFIED: product Requirements §6.2.4; FlashQuery `src/mcp/tools/documents/write.ts`; product Test Plan §4.3.4 and §4.6.6]

REQ-012 URI helpers already exist in `src/main/flashquery/uri.ts` and tests exist in `src/main/flashquery/uri.test.ts`. Phase 3 should treat these as the canonical URI contract and avoid moving helper ownership unless import boundaries require a shared location later. [VERIFIED: `src/main/flashquery/uri.ts`, `src/main/flashquery/uri.test.ts`; product Requirements §6.3.1]

## Risks and Open Questions

- Dependency risk: Cate does not currently depend on `@modelcontextprotocol/sdk`. Adding it is the lowest-risk protocol implementation path, but it changes the dependency graph and should be an explicit plan task with lockfile review. [VERIFIED: `package.json`; Context7; npm registry]
- Registration lifecycle risk: subscribing globally to manager status for every workspace can leak handlers if not owned by a singleton. Prefer one `FlashQueryClientManager` instance and register the status-to-IPC bridge once inside `registerFlashQueryHandlers`, with tests proving duplicate registration is not introduced. [ASSUMED]
- Workspace mutation duplication risk: `updateWorkspace` already stores/clears tokens when `flashqueryConnection` changes. If `flashquery:setConnection` also calls `setWorkspaceToken`, tests may pass while doing duplicate writes. Planner should choose one owner, preferably workspace manager persistence, unless a narrower helper is extracted. [VERIFIED: `src/main/workspaceManager.ts`]
- Status-on-clear choice: product docs allow either a no-connection broadcast or no broadcast on clear. Recommendation is a deterministic disconnected payload with error text like `No FlashQuery connection is configured for this workspace`, because it gives all renderer windows immediate state convergence and is easier to test. [VERIFIED: product Requirements §6.2.1; ASSUMED recommendation]
- Tool response shape risk: FlashQuery MCP tools return JSON strings in `content[0].text`; Phase 3 should parse and validate those envelopes instead of passing MCP raw content to renderers. Exact `list_vault` entry fields should be confirmed against the current FlashQuery `list_vault` JSON output while implementing. [VERIFIED: FlashQuery `src/mcp/utils/response-formats.ts`, `src/mcp/tools/files.ts`]
- Node version risk: this environment currently ran npm with Node `v24.7.0`, while Cate requires `>=20 <23`. Planning should require Node 20/22 before dependency or lockfile work. [VERIFIED: local npm output; `package.json`]
